# ZP10D 物理仿真与 GPU 热点实测（2026-10-18）

当前训练的主要开销是 MJX 接触约束求解，优先优化其线搜索和归约计算。物理相关内核约占累计 GPU 内核时间的 **95.59%**，其中求解器约占 **84.42%**、线搜索约占 **53.57%**。这是当前新机器人及其训练接触近似的实测结果。

## 测试条件与验证

- MX350，2,048 MiB 专用显存，Pascal 6.1，驱动 582.78；Python/JAX/MJX/Brax 版本见 `environment.json`。
- 512 环境，优化奖励，unroll 16，batch 512，每批 2 次 PPO 更新；控制周期 20 ms，物理周期 2 ms，10 个物理子步。训练场景为 17 个身体包围盒加地面，共 18 个 geom；省略自碰撞，完整模型为 3,296 个 geom。
- 从新策略开始，实际完成 49,152 环境步、6 轮 PPO，保存 6 个检查点。策略参数最大变化 0.0032935664；这仅验证训练与测量，不是行走验收。
- 前两轮仍含编译；第三、第五、第六轮未开启分析器，分别为 853.659、865.492、851.093 环境步/s，中位 **853.659 环境步/s**。
- 仅采集第四轮：8,192 环境步，训练计时 **10.312 s**，794.403 环境步/s。与未采集中位数相比，采集使单轮时间增加约 7.46%；启动分析器、首次导入及写出轨迹的额外时间不用于稳态吞吐估计。
- 完整诊断约 231.68 s，进程峰值 RSS 3.032 GB；cgroup 无 OOM 或内存上限触发。13 个输入文件在运行开始/结束时的 SHA256 相同，记录于 `profile.json`。
- 本轮仅加入分析标签与采集/解析脚本；控制周期、物理参数、求解器、奖励和 PPO 配置没有因分析而调整。

## GPU 实际耗时

JAX/CUPTI 成功采集真实设备事件，原始 XPlane 无警告或错误。统计到 **190,086 次计算内核**，累计 **9.221 s**；GPU 事件跨度 10.442 s、事件时间并集 9.233 s。时间并集包含传输与回调边界，不能直接当作硬件计算单元利用率。

下表的分母是累计 GPU 计算内核时间，不是训练端到端时间。每个内核只计一次；融合内核按其编译标签归属，跨模块融合单列。

| 模块 | 内核累计时间 | 占比 |
|---|---:|---:|
| 接触求解：线搜索 | 4.939 s | 53.57% |
| 接触求解：梯度、Hessian 与分解 | 1.411 s | 15.30% |
| 接触求解：其余计算 | 1.335 s | 14.47% |
| 接触求解：约束更新 | 0.100 s | 1.08% |
| 其余物理计算 | 0.970 s | 10.52% |
| 碰撞检测 | 0.060 s | 0.65% |
| 跨模块融合 | 0.345 s | 3.74% |
| 其余采样 | 0.040 s | 0.44% |
| 奖励 | 0.007 s | 0.08% |

CUDA Graph 内核常缺少直接标签。解析器从本次 XPlane 保存的 HLO、program ID 与内核名恢复标签；库内核通过 correlation ID 关联主机启动事件及其外层作用域。仍有 3.74% 跨模块融合和 0.056% 未归属时间；不能把表中的 PPO 标签占比当作整个网络更新的精确耗时。

主机时间线提供独立佐证：10 个物理子步的外层范围合计 **10.261 s**，其中求解器迭代范围合计 **9.848 s**，约为该轮训练计时的 **95.50%**。这些范围包含设备计算、调度和等待，彼此嵌套，不能与 GPU 内核时间相加。

## 值得先处理的计算

1. **线搜索的三个归约内核合计占全部内核时间 49.39%。** `input_reduce_fusion_1` 为 2.392 s / 11,290 次；`loop_compare_reduce_fusion` 为 1.117 s / 1,129 次；`loop_compare_multiply_fusion` 为 1.046 s / 11,290 次。优先检查这些融合计算中的重复表达式、归约布局和条件执行。
2. **求解器并没有跑满 50 轮。** 本轮有 16 次控制更新 × 10 个物理子步，即 160 个 512 环境批次；求解器共执行 1,129 轮，平均 **7.056 轮/批次**，范围 **6～9 轮**（6:23、7:108、8:26、9:3）。这是批处理循环轮数，不能解释为每个环境各自的收敛轮数。将上限从 50 降到 20，按本次轨迹不会减少已观察到的迭代。
3. **每轮线搜索执行完整的 10 次扫描。** 上述两类内核各出现 11,290 次，恰为 1,129 × 10。MJX `_while_loop_scan` 使用固定长度 scan；其逐环境条件经过 vmap 后以选择操作保留状态，保存的编译体里没有能逐环境跳过整段计算的 conditional。可以先测量全批次何时全部收敛，再评估使用批次整体提前退出是否能省下后续扫描；当前轨迹没有记录逐环境线搜索收敛轮数，尚不能断言能省多少。
4. **小内核数量多，但主要耗时仍集中在上述归约。** 内核时长中位数 2.88 μs；小于 10 μs 的占调用次数 67.99%，却仅占内核累计时间 **3.60%**。CUDA Graph 已经启用；不能仅凭内核数量就认定启动开销是第一瓶颈。

直接设备传输累计约 11.6 ms；每次检查点保存中位 114 ms，参数检查单次约 3～11 ms。本次未观察到它们主导训练计算。正式训练的评估被本次 `--no-eval` 排除，长期训练仍应另看评估开销及保存频率。

## 优化顺序与验收

1. 保持 2 ms 物理步和求解精度，先针对上述归约核检查计算复用与布局，并测量线搜索提前退出的可行性。候选必须与原实现比较相同输入下的加速度、接触力、状态轨迹、收敛条件与稳态吞吐。
2. 若需要测试 `ls_iterations=5` 等较小上限，将其作为单独的数值精度实验；对照接触穿透、力矩、跌倒/恢复和完整 2 ms 模型回放，不能仅凭吞吐采用。这个改动本轮没有实施。
3. 之后再测试 8 或 5 个物理子步。它影响整个接触积分过程，验证范围更大；本轮数据已经指出更集中的优化目标。
4. Python 重写、权重 FP16/INT8 或缩小网络的优先级较低：物理计算已在 JAX 编译的 GPU 程序内，当前占主导的是接触求解。

作为收益量级参考：若仅把线搜索的内核时间减半，按当前占比，累计内核时间的理论加速约为 **1.37 倍**；端到端收益仍需实测。没有 Nsight 硬件计数器，本次不能进一步断言热点究竟受显存带宽、指令吞吐还是寄存器使用限制。当前是早期策略的一轮时间线，学习后的接触状态与求解轮数可能变化，需要在稳定策略上复核。
